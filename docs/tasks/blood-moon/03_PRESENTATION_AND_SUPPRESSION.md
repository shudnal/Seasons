# Blood Moon — presentation and suppression

Обязательная часть задачи `CHAT_2026-08-23_BLOOD_MOON_FIRST_VERTICAL_SLICE.md`.

# 9. Forewarning и Marked

## 9.1. Forewarning

Текстового сообщения недостаточно. Игрок должен заранее заметить, что с осенью происходит что-то неправильное, даже если впервые не понимает точных правил.

В первом срезе реализовать минимум один **не текстовый внутриигровой** признак на каждой ночи configured forewarning range:

- использовать тот же Blood Moon environment overlay и/или cloud VFX на низкой интенсивности;
- эффект действует только ночью;
- интенсивность постепенно растёт от первой ночи предвестия к последней ночи перед финальной;
- не устанавливать forced environment;
- не включать боевые modifiers, spawn, SoftDeath или блокировку сна;
- точную силу держать в одном легко настраиваемом месте, а не размазывать по patches;
- предупреждение/center text допустимы как дополнительный слой, но не как единственная индикация.

Простая стартовая формула допустима:

```text
lastForewarningDay = effectiveFinalEventDay - 1
forewarningDayFactor = InverseLerp(firstForewarningDay, lastForewarningDay, currentAutumnDay)
nightFactor = 0..1..0 в пределах ночи
visualFactor = forewarningDayFactor * nightFactor * lowForewarningCap
```

`lowForewarningCap` должен оставаться заметно слабее финального перехода 18:00–23:00. Значения будут отлаживаться владельцем мода в реальной игре.

Допустим один редкий DreamText/сон-предвестие за год, но он не является обязательным условием первого среза и не заменяет изменение мира.

Не превращать forewarning в подробный tutorial. Первый Blood Moon может застать игрока врасплох и закончиться неудачно; цикличность Seasons должна позволить лучше подготовиться в следующий год.

## 9.2. Marked в 18:00

При входе в Marked:

1. зафиксировать enrollment текущих игроков;
2. остановить и подавить `RandEventSystem`;
3. заблокировать сон;
4. добавить/обновить Blood Moon status effect;
5. начать линейный visual blend;
6. синхронизировать authoritative state;
7. залогировать transition один раз.

Status tooltip должен прямо объяснять минимум:

- в 23:00 начнётся бой;
- сон недоступен;
- позже здесь будет доступен Blood Craft;
- смерть в активной фазе не отнимет навыки и завершит личное участие.

Blood Craft в этом срезе ещё не реализуется; формулировку про него можно держать выключенной до соответствующей задачи либо добавить отдельный placeholder localization token, не обещающий неработающую механику пользователю.

# 10. RandEventSystem

Blood Moon реализуется полностью собственной системой. Не создавать и не подменять `RandomEvent`.

## 10.1. Suppression window

С 18:00 (`Marked`) до полного завершения morning resolution:

- остановить текущее событие RandEventSystem;
- не позволять запускать новые random events;
- не позволять запускать/продолжать forced events RandEventSystem;
- не позволять `RandEventSystem` переопределять environment/music/event state Blood Moon.

В начале Marked сервер должен корректно остановить существующее событие через штатные методы, где возможно, а не только обнулить визуальный указатель на клиенте.

После resolution вернуть систему в обычный режим, но не форсировать немедленный запуск нового raid.

## 10.2. Patch policy

Патчи должны быть узкими и включаться только пока authoritative Blood Moon suppression active.

Не оставлять глобально отключённый RandEventSystem при исключении, reload или смене мира. Cleanup обязан быть в `finally`/world unload paths.

## 10.3. Карта

Не рисовать raid circles, восклицательные знаки и другие map markers.

Группировка — скрытая механика, которую игрок должен чувствовать только по плотности и составу боя.

# 11. Визуальная среда

Визуальная часть должна быть изолирована в отдельном компоненте/namespace, чтобы владелец мода мог дальше самостоятельно подбирать и отлаживать VFX в реальной игре.

Не добавлять сторонние ассеты.

## 11.1. Blood Moon EnvSetup

После доступности `EnvMan`:

1. найти ванильный environment `Fader`;
2. создать отдельную копию, не мутируя оригинал;
3. дать уникальное внутреннее имя, например `Seasons_BloodMoon`;
4. для каждого поля типа `Color` в копии установить `color.r = 1.0f`, сохранив остальные компоненты;
5. установить:

```csharp
m_windMin = 1f;
m_windMax = 2f;
m_sunAngle = 70f;
```

6. зарегистрировать environment один раз на текущую world/session;
7. корректно удалить/разрегистрировать копию при unload.

Эти значения уже проверены владельцем мода в игре.

## 11.2. Плавный overlay 18:00–23:00

До 23:00 не форсировать новый environment.

Текущая реальная погода должна постепенно получать Blood Moon overlay:

```text
18:00 factor = 0
23:00 factor = 1
```

На первом этапе коэффициент строго линейный по авторитетному schedule.

Интегрировать overlay в существующий transient patch `EnvMan.SetEnv`, где Seasons уже сохраняет значения `EnvSetup`, временно меняет luminance, вызывает vanilla и восстанавливает исходный объект.

Порядок:

```text
original current environment
→ existing seasonal luminance modifications
→ Blood Moon transition toward copied target environment
→ vanilla SetEnv
→ restore all original fields
```

Blood Moon overlay не должен зависеть от `controlLightings` или наличия texture controllers.

Дополнить сохранение/восстановление как минимум полями:

```text
m_windMin
m_windMax
m_sunAngle
```

Не выполнять reflection по всем Color fields на каждом кадре: reflection допустим при одноразовом построении target, а горячий Apply должен использовать кэшированные delegates/явные поля/другой дешёвый подход.

## 11.3. Forced environment с 23:00

В `Active`:

- прекратить старую погоду;
- установить собственный Blood Moon environment через штатный force-environment механизм;
- держать его до resolution;
- не позволять дождю/снегу/обычным environment overrides ухудшать видимость и боевую эффективность.

Реализовать ownership/lease:

- сохранить предыдущее значение force environment;
- считать Blood Moon владельцем force только пока текущее значение равно собственному имени;
- при cleanup не затирать force environment, который другой мод успел изменить после нас;
- при нормальном завершении восстановить допустимое предыдущее значение либо очистить force, если до события его не было.

Каждый клиент применяет force environment из авторитетной фазы; серверный state остаётся источником истины.

## 11.4. Ashlands_FaderFX

Создать локальную копию ванильного `Ashlands_FaderFX`.

В копии оставить только визуальные ветки:

```text
cloud
cloud (1)
```

Допускается безопаснее отключить остальные render/particle ветки, чем разрушить неизвестные промежуточные parent transforms.

Для ParticleSystem в этих ветках:

- использовать `main.startColor`;
- установить красный канал используемого цвета в `1.0f`;
- не писать сложную обработку gradients/ColorOverLifetime: владелец уже проверил, что нужный prefab фактически использует простой main start color;
- сохранить исходные emission multipliers;
- с 18:00 до 23:00 плавно умножать emission на visual factor;
- с 23:00 держать полную интенсивность;
- при cleanup остановить emission и очистить частицы под fade.

Не создавать и не искать объекты каждый кадр.

## 11.5. Music/SFX

В этой итерации не писать финальную музыку и не добавлять внешние клипы.

Оставить одну чистую точку интеграции для будущих нескольких треков по состояниям, но не добавлять неиспользуемую абстракцию ради абстракции.

# 12. Blood Moon status и SoftDeath

## 12.1. Blood Moon status effect

Можно использовать один custom status effect с динамическими названием/tooltip/icon state либо несколько простых эффектов, если это лучше совпадает с текущей архитектурой Seasons.

Он должен ясно показывать:

### Marked

- countdown/приближение боя;
- сон заблокирован;
- краткое объяснение события.

### Active

- Bloodlust progress;
- текущие боевые modifiers первого среза;
- отсутствие skill loss при смерти;
- смерть завершает личное участие.

### GoalReached

- 100% достигнуто;
- полный buff сохраняется;
- враги предпочитают незавершивших игроков;
- можно помогать группе.

Не полагаться только на center message: постоянный SE нужен для понятности.

## 12.2. SoftDeath

В момент перехода участника в активную боевую фазу добавить ванильный status effect `SoftDeath` через штатный `SEMan` API.

Требования:

- игрок сразу видит, что смерть не вызовет потери навыков;
- SoftDeath должен гарантированно покрывать всю активную длительность 23:00–05:45;
- при необходимости обновлять duration безопасно;
- не уничтожать чужой/pre-existing SoftDeath безусловно;
- при смерти позволить vanilla выполнить обычный death flow без skill drain;
- смерть сразу фиксируется сервером как outcome `Death` и завершает личное участие;
- игрок не возвращается в текущий event после respawn/reconnect.

При cleanup выживших удалить только тот SoftDeath, владение которым можно безопасно отнести к Blood Moon. Если надёжно отличить его нельзя, предпочесть не ломать ванильную защиту после недавней смерти.
